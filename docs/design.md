# swingcheck 設計書（Android 初期版）

仕様は [spec.md](spec.md) を参照。この文書は、仕様をどう作るかを決める。
判定ロジックと計算式（4〜7章）は、iOS 版でも同じ結果になるように OS に依存しない形で書く。

## 1. 構成

| モジュール | 種類 | 役割 |
|---|---|---|
| `:core` | Kotlin/JVM ライブラリ | 骨格データの型、平滑化、数値の計算、Pの判定、スイング検出、ボール判定、単位の換算。Android に依存しない |
| `:app` | Android アプリ | 画面（Jetpack Compose）、カメラ、MediaPipe の呼び出し、保存（Room、DataStore）、解析の順番待ち（WorkManager） |

- `:core` は JVM 上の単体テストだけで検証できるようにする。実機がなくても判定ロジックを作り込める
- MediaPipe は `:app` に閉じ込める。`:core` は「各コマの関節の座標」を受け取るだけにする
- 将来のサーバー解析やクラブ検出モデルは、`:app` の `PoseEstimator`／`ShaftEstimator` の実装を差し替えて対応する

パッケージ名は `jp.co.updates.swingcheck`（仮。公開前に決め直してよい）。

## 2. 処理の流れ

```
[撮影画面]
 カメラ ─┬─ エンコーダー ─ 圧縮済みデータのリングバッファ（直近 N 秒）
         ├─ プレビュー表示
         └─ 縮小画像（毎秒 15 コマ程度）─ MediaPipe ─ スイング検出（:core）
                                                        │ 検出
                                                        ▼
                                      リングバッファから前後を MP4 に書き出す
                                                        │
                                                        ▼
                                    Swing を保存（状態：解析待ち）→ 解析の順番待ちに入れる
[解析（WorkManager）]
 MP4 を全コマ読む ─ MediaPipe（VIDEO モード）─ 骨格の列を保存
   ─ 平滑化 ─ ボール判定 ─ Pの判定 ─ 各Pの数値を保存 ─ 状態：完了
   （ボール判定が「素振り」なら Swing ごと削除）
[解析結果の画面]
 動画 ＋ 骨格の列 ＋ Pのコマ ─ 表示。Pを直したら数値を計算し直して保存
```

### 撮影まわりの方針（実機で確認が必要）

- Camera2 を直接使う。120fps 以上は Camera2 の高速撮影セッション（constrained high speed）が必要で、このセッションは出力先が「プレビュー」と「動画エンコーダー」の 2 つに限られる
- そのため、カメラの出力は「エンコーダーの入力 Surface」と「SurfaceTexture」の 2 つにする。SurfaceTexture は OpenGL で画面に描き、あわせて毎秒 15 コマ程度だけ縮小して読み出し、MediaPipe に渡す
- エンコード済みのデータ（H.264）をメモリ上のリングバッファに保持し、スイングを検出したらキーフレームの位置から MP4 に書き出す（MediaMuxer）
- 60fps 以下では通常のセッションでも同じ構成で動かす（構成を 1 つにまとめる）
- カメラは、最初の背面カメラ（通常はメイン）と焦点距離が同じものだけを候補にし、超広角・望遠は高速撮影に対応していても選ばない（ゆがみが解析に向かない）。候補の中で最大の fps（AUTO）を選び、高速撮影ができなければメインカメラの通常セッション（60／30）にする
- 開始に失敗した（セッション作成の失敗、開始直後 5 秒以内のカメラのエラー）ときは、240 → 120 → 60 → 30 の順に次の設定でやり直す。カメラ・セッションの種類・fps で失敗した設定は DataStore に記録して次回から除外し、開発用画面で一覧とリセットができる
- 実機確認の前に、端末が対応する高速撮影のサイズとフレームレートを一覧表示する開発用の画面を用意する

## 3. 座標と向き

- MediaPipe Pose Landmarker の画像座標（x, y は 0〜1、y は下向き）を、動画の幅と高さを掛けてピクセル座標に直してから計算する（縦横比で角度がゆがまないようにする）
- 背面カメラの映像は左右反転していない前提。正面撮影の右打ちでは、目標方向（飛球線の先）は画面の右（+x）になる
- MediaPipe の left／right は「本人から見た左右」。右打ちでは、本人の左＝リード側（目標側）、右＝トレイル側
- 移動量の符号は GEARS に合わせる：Sway は目標方向が正、Lift は上が正
- 左打ち対応のときは、ここで x を反転し left／right を入れ替えるだけで済むようにする（`Handedness` を 1 か所で扱う）

使う関節（MediaPipe の番号）：

| 番号 | 関節 | 番号 | 関節 |
|---|---|---|---|
| 0 | 鼻 | 7／8 | 左耳／右耳 |
| 11／12 | 左肩／右肩 | 13／14 | 左肘／右肘 |
| 15／16 | 左手首／右手首 | 19／20 | 左人さし指／右人さし指 |
| 23／24 | 左腰／右腰 | 25／26 | 左膝／右膝 |
| 27／28 | 左足首／右足首 | | |

## 4. 前処理

1. **欠損の補間**：visibility が 0.5 未満の関節は、前後のコマから線形補間する。前後どちらかにしかなければその値を使う
2. **平滑化**：One Euro Filter（mincutoff = 1.0、beta = 0.05、dcutoff = 1.0 を初期値とし、実データで調整する）。インパクト前後の速い動きを鈍らせすぎないよう、手首と指は beta を大きめ（0.3）にする
3. 以降の計算はすべて平滑化後の座標で行う

派生する点：

| 点 | 定義 |
|---|---|
| 頭 | 鼻・左耳・右耳の、visibility で重み付けした平均 |
| 肩の中心 | 左肩と右肩の中点 |
| 腰の中心 | 左腰と右腰の中点 |
| 手 | 左右の手首と左右の人さし指、計 4 点の平均 |
| 基準の長さ `S` | P1 での肩幅（左肩と右肩の距離、ピクセル） |

## 5. 数値の計算

角度は度、移動量はピクセルで計算し、表示のときに比率や cm に直す。

| 項目 | 計算式 |
|---|---|
| Head Sway | `head.x − head(P1).x` |
| Head Lift | `−(head.y − head(P1).y)` |
| Shoulder Tilt | トレイル肩からリード肩へのベクトルの、水平からの角度。リード肩が高いと正 |
| Pelvis Side Bend | トレイル腰からリード腰へのベクトルについて、Shoulder Tilt と同じ定義 |
| Pelvis Sway | `hipCenter.x − hipCenter(P1).x` |
| Spine Tilt | 腰の中心から肩の中心へのベクトルの、鉛直からの角度。肩の中心がトレイル側（目標と反対）に傾くと正 |
| Knee Flex（左右） | `180° − ∠(腰, 膝, 足首)`。まっすぐで 0 |
| Elbow Flex（左右） | `180° − ∠(肩, 肘, 手首)`。まっすぐで 0 |

- 右打ちの正面撮影では「リード＝画面の右側」なので、角度は目標方向を +x として計算する
- 移動量の比率表示：`移動量 ÷ S × 100`（%、「肩幅の◯%」）
- cm 表示：`cmPerPx = 身長(cm) × 0.259 ÷ S`。0.259 は身長に対する肩幅（両肩峰間の幅）の比率の一般的な値。MediaPipe の肩の点は肩峰と完全には一致しないので、実データで係数を調整する
- インチ表示：cm ÷ 2.54。身長はフィート・インチで入力し、内部では cm で持つ

## 6. シャフトの推定（初期版：骨格のみ）

- 推定シャフトの向き：リード側の前腕（肘→手首）の向きを、そのまま手の位置から延長したもの
- 長さ：`1.5 × S`（表示用の目安）
- バックスイング初期（P2）とフォロー（P8）では手首の折れが小さいので、おおむね近い向きになる。トップやダウンスイングでは手首が折れているため大きくずれる。P6 の判定ではこの推定を使わない（7章）
- P8 ではトレイル側の前腕（右肘→右手首）を使う（フォローでは右腕が伸びてシャフトと一直線に近づくため）
- 将来のクラブ検出モデルは、この推定を置き換える `ShaftEstimator` として入れる

## 7. Pの自動判定

手の位置 `hand`、手の速さ `v`（ピクセル／秒、`S` で割って正規化）を使う。対象はスイング 1 回分の動画。

| P | 判定 |
|---|---|
| 区間 | 手の速さが最大のコマ（インパクト付近）より前で、手の高さが最も高くなるコマを仮のトップ T とする。T より前をバックスイング、後をダウンスイング以降とする（フィニッシュで手がトップより高くなる人への対策） |
| P1 | T より前で、正規化した手の速さが 0.3 S/秒 未満の状態が 0.3 秒以上続いた最後の区間の、最後のコマ |
| P2 | P1〜P3 の間で、推定シャフト（リード前腕の向き）がトレイル側を向いて水平を横切るコマ |
| P3 | P1〜T の間で、リード腕（リード肩→リード手首）が水平を横切るコマ |
| P4 | T（手が最も高いコマ）。手の動きが止まって向きが変わるコマが近くにあれば、そちらを優先する |
| P5 | P4 より後で、リード腕が水平を横切るコマ |
| P6 | P5〜P7 の間で、手の高さが P2 での手の高さに戻ったコマ |
| P7 | P5 より後で、手が P1 での手の位置に最も近づくコマ（手が速く動いている区間に限る） |
| P8 | P7 より後で、推定シャフト（トレイル前腕の向き）が目標側を向いて水平を横切るコマ |

- 「横切る」コマは、角度の符号が変わる前後 2 コマのうち、水平に近いほうとする
- 見つからなかったPは、前後のPの中間のコマを入れ、「推定できなかった」印を付ける
- P1 < P2 < … < P8 の順になるように、順番が崩れたPは前後のPの中間に置き直し、同じ印を付ける
- P1 を決める前は S（P1 での肩幅）が使えないため、判定中は動画の先頭 20% のコマの肩幅の中央値を暫定の S とする
- 手の速さは、前後 0.03 秒離れた 2 点の差から求める（フレームレートによらず同じ尺度にする）
- P7 は、手の速さが 3 S/秒 以上の区間に限る
- 順番が崩れたときは、P1〜P8 の中で順番どおりに並ぶ最も長い組を残し、外れたPを前後の中間に置き直す
- 判定に使う閾値はすべて 1 か所の設定値（`PhaseDetectorConfig`）にまとめ、実データで調整する

## 8. スイングの検出（撮影中）

毎秒 15 コマ程度の骨格で、次の状態遷移を回す。

```
IDLE ──全身が映っている──▶ READY
READY ──手の速さ < 0.3 S/秒 が 0.4 秒続く──▶ ADDRESS
ADDRESS ──手が動き始める（> 0.6 S/秒）──▶ MOVING
MOVING ──手が肩の中心より上に上がる──▶ SWING
MOVING ──上がらずに止まる（< 0.3 S/秒 が 0.2 秒）──▶ ADDRESS（ワッグルや構え直しとみなし、アドレスの開始時刻を更新）
MOVING ──1.0 秒たっても上がらず、止まりもしない──▶ READY
SWING ──手の速さ < 0.3 S/秒 が 0.4 秒続く──▶ 検出：［ADDRESS の開始 − 0.5 秒, 今 + 0.3 秒］を切り出す ─▶ READY
SWING ──3.0 秒たっても止まらない──▶ 検出として扱う（フィニッシュで止まらない人への対策）
どの状態でも ──全身が 1.0 秒以上映らない──▶ IDLE
```

- 全身が映っているとみなすのは、鼻・両肩・両手首・両腰・両膝・両足首の visibility がすべて 0.5 以上のとき
- 切り出しの開始時刻はリングバッファより前になることがあるので、呼び出し側でバッファの先頭に合わせる
- リングバッファの長さは 6 秒とする（アドレスでの静止＋スイング＋余白が入る長さ）
- 閾値は `SwingDetectorConfig` にまとめる

## 9. ボール判定（素振りの除外）

動画の明るさ（グレースケール）を使う。

1. **探す範囲**：P1 のコマで、左右は「両足首の x の間 ± 0.3 S」、上下は「足首の y − 0.15 S 〜 足首の y + 0.35 S」
2. **ボールを探す**：範囲内で、周囲より明るい小さな塊を探す。直径の目安は `0.11 S`（ボール直径 42.67mm ÷ 肩幅の目安 約 40cm）の 0.6〜1.6 倍。丸さ（面積 ÷ 外接円の面積）が 0.6 以上のもののうち、最も明るいものを選ぶ
3. **消えたか調べる**：最後のコマ（フィニッシュ後）で、同じ場所の平均の明るさと、周囲の明るさとの差を比べる。P1 での差の 40% 未満に下がっていれば「消えた」とする
4. 結果は `HIT`（打った）、`PRACTICE`（素振り）、`UNKNOWN`（ボールが見つからない、暗い、など）の 3 つ
5. `PRACTICE` のときだけ保存しない。設定でオフのときは判定しない

### 動画の読み込み

`VideoImporter`：選んだ動画をアプリの領域にコピー → `VideoFrameReader.probe`（実測 fps、長さ、メタデータの撮影時 fps） → `ImportPolicy.judge`（Android に依存しない判定。10 秒超は拒否、撮影時 fps ÷ 実測 fps が 1.5 以上なら timeScale を設定）→ `source = IMPORTED` で登録して解析の順番待ちへ。拒否・失敗のときはコピーを消す。読み込んだ動画はボール判定をしない。

## 10. データ

### Room

`swing`

| 列 | 型 | 内容 |
|---|---|---|
| id | Long | 主キー |
| createdAt | Long | 撮影日時（エポックミリ秒） |
| videoPath | String | アプリ専用領域の MP4 の相対パス |
| fps | Float | 実際のフレームレート |
| frameCount | Int | コマ数 |
| width, height | Int | 動画のサイズ |
| cameraView | String | `FACE_ON`（将来 `DOWN_THE_LINE`） |
| handedness | String | `RIGHT`（将来 `LEFT`） |
| heightCm | Float? | 身長 |
| memo | String | メモ |
| analysisStatus | String | `PENDING` / `RUNNING` / `DONE` / `FAILED` |
| ballResult | String? | `HIT` / `PRACTICE` / `UNKNOWN` |
| analysisVersion | Int | 判定ロジックの版。版が上がったら再解析できるようにする |
| source | String | 取り込み元。`CAPTURED`（アプリ内撮影）/ `IMPORTED`（読み込み）。既定は `CAPTURED` |
| timeScale | Float | 動画の時刻から実時間への補正倍率（実時間 = 動画の時刻 ÷ timeScale）。既定は 1。引き延ばされたスロー動画の読み込みだけ 1 より大きい |

- fps は補正後（実時間）の値で持つ
- 補正は解析に使うときだけ行う。骨格ファイルの各コマの時刻と、再生（ExoPlayer のシークとコマ番号⇔時刻の変換）は動画の時刻のまま。解析（平滑化、手の速さ、Pの判定）は、骨格ファイルを読むときに時刻を `÷ timeScale` した列を使う（`SwingRepository.loadPose`、解析の流れ）
- スキーマ版 2 で `source`、`timeScale` を追加（マイグレーション 1→2。既存の行は `CAPTURED`、1）

`position_mark`（スイングごとに P1〜P8 の 8 行）

| 列 | 型 | 内容 |
|---|---|---|
| swingId, position | Long, Int | 主キー（position は 1〜8） |
| autoFrame | Int | 自動判定のコマ |
| manualFrame | Int? | 手で直したコマ。null なら自動 |
| autoUncertain | Boolean | 自動判定できなかった印 |
| metricsJson | String | そのPの数値（項目名→値）。比較機能のために保存する |

骨格の列は Room に入れず、スイングごとにファイル（`pose/<id>.bin`）に保存する。形式は「コマ数 × 33 関節 × (x, y, z, visibility)」の float32 配列に、先頭にヘッダ（版、コマ数、各コマの時刻）を付けたもの。

### DataStore（設定）

| キー | 初期値 |
|---|---|
| fpsMode | `AUTO`（ほかに 30／60／120／240） |
| defaultHeightCm | 未設定 |
| lengthUnit | 端末の地域が米国・英国などなら `INCH`、それ以外は `CM` |
| practiceFilterEnabled | true |

## 12. テスト

- `:core`：合成した骨格の列（P1〜P8 の姿勢を補間して作ったスイング）で、Pの判定、数値の計算、スイング検出を検証する
- ボール判定：合成したグレースケール画像（白い円のあり／なし）で検証する
- 実データが手に入ったら、手で付けた正解のPのコマとの差（コマ数）を測るテストを追加する
